# Radix — Implementation Decision Log

Decisions with spec rationale; ambiguities resolved via doc 11 open questions. Entries are append-only; supersessions noted.

## Architecture

- **D1 Numeric core = `rug` (GMP/MPFR/MPC).** Doc 03's semantics are the observable behavior of MPFR/MPC/mpq: round-to-nearest at P bits (default 2000), trunc-based `frac`, complex branches, exact rational shadow ("GMP rationals"). `rug` exposes the same primitives; a pure-Rust engine would need correctly-rounded complex transcendentals re-derived from scratch. Radix is GPL-3.0-or-later, compatible with the LGPL libraries (licensing history: D26 switched Radix to MIT; D34 supersedes D26, restoring GPL-3.0-or-later). Deviation from "avoid unnecessary dependencies": justified by task §4.A ("essential", "nontrivial").
- **D2 Number model.** `Number { re: Float, im: Float, exact: Option<Rational> }` at precision P. The rational shadow is carried only for real values exactly equal to p/q; `+ − × ÷` between two shadowed values stays exact (shadow recomputed, MPFR part re-rounded); any op that can be inexact (functions, roots, complex results, general powers) drops the shadow. Negative zero normalized to +0 everywhere. MPC used internally for transcendentals, with the documented +π branch corrections applied after.
- **D3 Parser = recursive descent straight off doc 02 §5's precedence table**, including the non-conventional levels (implicit-multiply/× at 4 below ÷/mod at 5; not at 6; function application at 7; bitwise/shifts at 8; % at 9; unary−/^/roots at 10; ! at 11). Percentage sugar (D6) at the additive level.
- **D4 Workspace:** `radix-core` (lib) + `radix-cli` (bins `radix`, `radix-cmd`) + `radix-gui` (bin) + `radix-search-provider` (bin, later). Engine has no GTK dependency.

## Ambiguity resolutions (OQ refs)

- **D5 OQ-02 precision split.** Evaluation context carries `precision` explicitly: GUI window context = 2000 bits; `--solve`, `radix-cmd`, search provider = 1000 bits (library default), as doc 08 §4 verifies. Deviation would be unifying at 2000 — rejected; spec says keep the distinction and record it.
- **D6 OQ-04 percentage sugar.** Implemented rule: for `a ± R` where R is *exactly* a bare postfix-percent node (`X%`), evaluate `a·(1 ± X/100)`. For compound right subtrees containing `%` (e.g. `20% * 100`), plain postfix evaluation applies. Verified equivalent to every asserted upstream case: `100±1%`=101/99, `140+15%`=161, `(((100−20)−50%)+20)`=60, `(50+50)+10%=`=110, and `100 - 20% * 100`=80 / `100 + 20% * 100`=120 / `100 - 100 * 20%`=80 (identical under both readings because a=100 in all asserted cases). Other combinations are implementation-defined (OQ-04 says derive from parser algorithm, test only asserted cases).
- **D7 Unit-token lifecycle.** Lexer classifies words as operator/function/currency/unit/variable per doc 02 §4. Parser rules derived from observable tests: `N unit in unit` → conversion; `N UNIT` without `in` → INVALID (UNIT-T013); bare unit word → variable reference (`m` → UNKNOWN_VARIABLE, UNIT-T017); `°`-prefixed unit tokens never reclassified (`˚C` bare → INVALID, UNIT-T018); unknown word adjacent to `in` → from-unit position → UNKNOWN_UNIT (UNIT-T014); `in` as inch-symbol vs keyword disambiguated by lookahead (`1 in in cm` = 2.54) — implementation-defined edge.
- **D8 OQ-03 automatic threshold.** `leading_digits` = 12 for base 10 pinned (spec: verified default; GUI never changes it). Bases 2/8/16 use 64/22/16 on total rendered digit count; base 10 threshold applied to integer-part digits of the fixed rendering (interpretation recorded; catalog cases FMT-T006..009 are the acceptance tests).
- **D9 OQ-07 multi-window history.** Each window holds its own tape and writes it at close; last close wins (matches documented per-window write; merge logic not invented).
- **D10 OQ-16 RSD fixed rate.** Implemented exactly as documented: RSD value = EUR-value ÷ 0.0085 (and XAF=XOF ÷ 0.00152449 in the same fixed block), applied when ECB file lacks the currency.
- **D11 OQ-01 error strings.** Only doc 05 §4 strings implemented. Dogtail's stale strings are ignored.

## Deviations (deliberate, recorded for handoff)

- **D12 Persistence paths.** Radix uses its own XDG dirs: `$XDG_DATA_HOME/radix/registers`, `$XDG_DATA_HOME/radix/custom-functions`, `$XDG_CACHE_HOME/radix/<provider files>`, config at `$XDG_CONFIG_HOME/radix/`. Formats identical to doc 08 §2 (including `×10¹²`-style superscript exponent encoding in registers). Rationale: writing into `gnome-calculator/`'s live data would mutate another application's state; content-format compatibility is kept so files are interchangeable.
- **D13 Settings backend.** Same keys/defaults/write-moments as doc 08 §1, stored via a keyfile at `$XDG_CONFIG_HOME/radix/settings.ini` (history tape serialized inside it). A GSettings schema file is shipped for future native integration; the store is behind a trait so the backend is swappable. Deviation from "GSettings/dconf" noted against STATE-001.
- **D14 Localization.** v1 ships English (C locale) strings with all user-visible text centralized in a catalog module; `in`/`to` keywords looked up through the catalog (so translation injection is a data change). LOC-T005 satisfied for C locale; other locales deferred.
- **D15 Naming.** Product/window title "Calculator" per spec; binary names `radix`/`radix-cmd`; `--version` prints `Radix <version>` (version mirrors upstream 51.1 for test parity of the format, not identity). App id `org.gnome.Radix` to avoid colliding with the original's desktop identity.
- **D16 Currency URLs.** Provider downloads use `https://exchange-api.gnome.org/...` as documented; exact sub-paths were not fully specified (`…` in doc 04), so Radix uses `https://exchange-api.gnome.org/<ecb|imf|unt|boc>` and treats format drift as a provider concern (OQ-06). Offline behavior is the tested contract.
- **D17 Scientific formats in non-decimal bases.** Doc 07 §2.3 ("falls back to fixed") and §2.5 (v51 "exponent of automatic/scientific overflow rendered in the current base") conflict; reconciled so every asserted case passes: *automatic* overflow in bases 2/8/16 renders scientific with the exponent in the current base incl. superscript `ᴬᴮᶜᴰᴱᶠ` (FMT-T008/009), while explicitly selected scientific/engineering in non-decimal bases render fixed with grouping (FMT-T011). Also decided: the base-suffix subscript appears on fixed renderings (incl. automatic-fixed) of real values when `repr_base ≠ parser_base`, never on scientific renderings or complex parts; the automatic threshold counts integer-part digits for base 10 (D8) and total rendered digits for bases 2/8/16; DMS carries are produced by one exact half-away rounding of total seconds (equivalent to the documented epsilon snapping at display scale).
- **D18 Search provider.** Implemented as a second binary `radix-search-provider` owning `org.gnome.Radix.SearchProvider` (per D15; spec's `org.gnome.Calculator.SearchProvider`) serving `org.gnome.Shell.SearchProvider2` at `/org/gnome/Radix/SearchProvider` via the **gio** D-Bus API already linked by GTK4 — the "zbus planned" dependency was dropped (no tokio, no new crates). Query pipeline reuses `--solve` normalization (D14 C-locale: `,` removed, radix `.`), rejects plain numbers/`=`/evaluation failures/50 ms budget, evaluates base 10 wordlen 32 angle-from-settings, renders AUTOMATIC accuracy 9. Metas and activation follow doc 08 §6 (description ` = <result>`, clipboardText, `edit-copy-symbolic`, 4 s notification withdraw via org.freedesktop.Notifications); open-in entries spawn `radix --equation <terms>`, preferring the sibling of the provider executable so an uninstalled build tree works. Activation degrades gracefully without a display (clipboard skipped, notification still attempted); the service idles out after 10 s. D-Bus service file shipped at `crates/radix-gui/data/dbus-1/services/` with an `@bindir@` placeholder for install-time substitution.
- **D19 gcalccmd numeric error codes.** `radix-cmd` prints `Error <numeric-code>` for non-MP errors, where the number is the `ErrorCode` discriminant (0 = NONE … 9 = RESOURCE_LIMIT). Doc 08 §5 does not enumerate the numbers, only the format; the discriminant order is fixed by doc 05 §3's error-class listing and is now ABI for `radix-cmd` output.
- **D20 Binary layout (supersedes D4's bin placement).** The shipped `radix` binary lives in `radix-gui` (window + headless `--solve` are one contract, doc 08 §4); `radix-cli` builds only `radix-cmd`. The early `radix-cli` stub bin named `radix` was removed: two workspace bins with the same name race for `target/debug/radix` and the stub could shadow the real binary after `cargo build --workspace`.
- **D21 App id and icon naming (deviation from doc 06 §1.3).** Doc 06 §1.3 carries upstream names (`org.gnome.Calculator`, `org.gnome.Calculator-symbolic`); Radix consistently uses `org.gnome.Radix` / `org.gnome.Radix-symbolic` per D15 across the .desktop file, the search-provider service/app icons, notification app-icon, and `--equation` window launch. Renaming back is a data-only change in the desktop/package files if a drop-in `org.gnome.Calculator` identity is ever wanted.
- **D22 Doc 13 visual layer — reconciliations and deviations.** The whole visual spec (doc 13) is implemented as one app stylesheet (`win.rs::load_css`) plus the libadwaita structure (ToolbarView raised, 700 px Clamp, breakpoint, AdwCarousel), runtime-audited against the §12 checklist with screenshots (see REQUIREMENT_COVERAGE "Doc 13 visual checklist"). Spec-internal conflicts resolved as follows:
  - *Keypad cell geometry.* §5.1's measured 64×44 px cells conflict with §5.2's `min-width/min-height: 64/44` + `padding: 2px 4px`: GTK's `min-width`/`min-height` exclude padding and the 1 px platform border, which rendered ~72×48 cells and overflowed the 336 px basic grid. Implemented `padding: 0; min-width: 62px; min-height: 42px` → exactly 64×44 rendered cells (the [M] measured values win; the padding rule is dropped).
  - *Bit panel sizing.* §6.4's `1.2em / min-width 20px` toggles cannot fit 64 bits (plus separators) in the 676 px keypad row (needs ≈1420 px). Deviation: 9 px bolder toggles, zero padding, 6 px nibble separators, 7 px byte markers — all 64 bits fit with slack. Markers sit in a two-row grid whose columns are whole bytes, keeping each marker over its byte group.
  - *Collapse threshold.* `MaxWidth` applies at ≤ the value, so the breakpoint uses 699 px to express doc 13 §6.1's "collapse strictly below 700 px" (advanced/financial/programming; the grids re-flow into an Adw.Carousel with page dots).
  - *Status/info row.* §4.3 specifies a non-editable TextView; implemented as a word-wrapping `Label` with the `status-view` class (same margins/min-height, platform `error` style for failures) — a Label cannot grow lines, which the status row never needs.
  - *Financial back button (§3.2).* Minimal semantics: hidden by default, shown while a financial result replaces the display, click hides it again (returns to the keypad). Doc 06 defines no deeper "financial display context" stack, so none was invented.
  - *Grid re-flow.* §6's "two 5-column grids side by side" wins over doc 06 §5's row lists where they disagree: the advanced 7-column rows are re-flowed across the two grids (numpad+operators left, functions right, `=` spanning two columns of the right grid), financial gets the ten dialogs on the left grid and extras/conversion on the right, programming splits 47 buttons across two grids. Button inventory is unchanged.
  - *Edge-to-edge collapse (§4.1).* "Side margins and radius collapse to 0 below the clamp's small threshold" — the threshold value is unspecified and the 360 px reference screenshot still shows 12 px margins, so the margins are constant 12 px; recorded as an open question for Team A rather than guessing a threshold.
- **D23 Reference-screenshot parity (GNOME 51 restyle).** The prompt owner supplied four GNOME 51 screenshots (basic side-by-side, advanced, conversion, financial) as the visual ground truth; the UI was re-verified against them and brought to parity:
  - *libadwaita stylesheet load (bug fix).* The app used `gtk::Application` and never called `adw::init()` — Adw widgets functioned but libadwaita's stylesheet never loaded, so everything rendered as stock GTK Adwaita (light, boxed buttons) regardless of color scheme. Switched to `adw::Application` (D20 binary unchanged). This, not any CSS issue, was the cause of the divergent look.
  - *Accent.* The reference pink is GNOME's pink accent (`#d56199` dark); the app simply follows the system accent like upstream — no hardcoding. Debug-only: `RADIX_DEBUG_ACCENT=<css-color>` pins the accent for screenshot comparison (bare Xvfb has no accent source; hook exists only in debug builds).
  - *Header.* Close button only (no minimize/maximize) per all four references — `gtk-decoration-layout: ":close"` set per display at activation.
  - *Keypad layouts reflowed to the references (doc 06 row lists lose where they disagree, consistent with D22's grid re-flow).* Basic and the right-hand page of advanced/financial share one `numeric_core`: `C ↑n ↓n ÷ mod / 789 × % / 456 − ( ) / 123 + = / 0 . x f(x)` with `=` spanning the bottom two rows and x / f(x) as MenuButtons (down chevrons; same popover content as before). Advanced left page: `⇧⁻¹ x² x^y conj x⁻¹ / sin sinh logᵧ Arg [x] / cos cosh log Re |x| / tan tanh ln Im x! / Deg π e i a×b`. Financial: the same math row, the ten dialogs as nested full-width thirds (`Ctrm Ddb Fv / Gpm Pmt Pv / Rate Sln Syd`), then Term (⅓) + Currency Conversion (⅔). Conversion: 3 columns (`C ⇅ ⌫` / digits / `0 . <contextual>`), the contextual cell being °′″ (angle), rate details (currency), π (other categories), or the hex A–F block (Number Base).
  - *Inverse pairings.* `x²↔y√`, `x^y↔y×10ˣ`, `x⁻¹↔x¹`, `sin/sinh/cos/cosh/tan/tanh ↔ ⁻¹`, `log↔10^x`, `ln↔e^x`, `Arg↔arg`, `Re↔re`, `Im↔im`. Dropped from the grids (keyboard input and shortcuts still work): `√`, `ⁿ√` (advanced), the conversion `+/−` sign button. `⇧⁻¹` is styled accent-tinted (`alpha(@accent_color, 0.15)` background, accent text; solid accent while checked).
- **D24 Layout parity round 2 (pixel-forensics vs the second screenshot batch).** A second set of side-by-side references exposed structural (not stylistic) deltas; each was root-caused against upstream 51.0 sources (`history-entry.blp`, `math-window.blp`, `math-converter.blp`, `buttons-conversion.blp`) before fixing. Supersedes D22's "edge-to-edge collapse is an open question" bullet — the reference confirmed the flush card, so the threshold is now implemented.
  - *History list background (the "dark band" bug).* GTK's ListBox paints its default dark `view` background behind the rows, covering the card tint. Load-bearing rule: `.history-view list { background: none; color: inherit; }` — rows then sit on the card with only `.history-entry`'s 1 px `@card_shade_color` top borders. The dark palette is compositional: the card is translucent (`@card_bg_color` = alpha(white,.08) over the window), `.history-view` adds `alpha(currentColor,.05)`, and the entry strip is the bare card — all sampled reference pixels reproduce from these three layers alone (no opaque colors invented).
  - *Small-mode flush card.* Upstream's Clamp applies `.small` below 700 px with `clamp > .small .display-container { margin: 0; border-radius: 0 }`; Radix now carries the same rule (plus `.small .bit-panel { border-radius: 0 }`) on a `content` Box that gets the class from a window breakpoint — below 700 the display/converter card hugs the window edges, above 700 it is inset 12 px with radius 12 (pixel-verified flush in both 360 px references).
  - *Bit panel moved into the display card.* The programming bit panel is appended to the card (not the keypad page) with a transparent background: the card shows through, the panel's `0 0 12px 12px` radius completes the card (square top corners via `.prog`), and it follows the card's margins in both clamp modes. `programming()` must NOT parent it (a widget gets one parent; the GTK append to the card silently fails otherwise).
  - *History rows = upstream's 7-column homogeneous grid.* Equation label spans cols 0–3 (wrap word-char, no ellipsize), dimmed `=` at col 4 (`max-width-chars: 1`, 12 px side padding), bold answer at cols 5–6 (`xalign 1`, ellipsize end, `max-width-chars 12`). This reproduces the reference's narrow-width behavior ("0.8333…" at 360, full digits at 700) — the homogeneity between equation and answer columns is what makes the ellipsis point move with width.
  - *Keypad pages are direct Stack children (upstream parity; no ScrolledWindow).* A ScrolledWindow reports a near-zero minimum, so the window's 616 px default never grew to fit the conversion keypad and its last rows clipped (the reference conversion window is ~638 px = header 46 + card 332 + 12 + keypad 236 + 12 — exactly the content minimum; a real WM grows the window, bare Xvfb cannot, hence the harness resizes to client+10). Only `keypad_area` margins (12 start/end/bottom) plus a per-page `margin-top: 12` remain.
  - *GTK4 Grid gotcha: hidden rows still count toward the minimum.* The conversion hex block sat in hidden rows 5–6, inflating the grid minimum to ~343 px and stretching every row (this, not fonts, was the "buttons too tall" delta). Upstream overlays two nested grids in the same 3×3 cell (`dec_buttons` visible ⇔ `hex_buttons` hidden); Radix now does the same (`digits_grid`/`hex_buttons` swapped in `update_hex_buttons`). Verified with a standalone measure repro: 5×3 = 236, 5×3+2 hidden rows = 324, nested-overlay = 236.
  - *The keypad never takes vertical extra space.* `keypad_area.set_vexpand(false)` (explicit): expand flags leak through a Stack even from hidden children (the collapsed-mode carousel's vexpand stretched rows on every page), and GTK BoxLayout gives children their natural size before dividing the rest among expanding children — so any keypad expand steals from the card/converter. With it pinned, the card (basic/advanced/…) or converter card (conversion) absorbs the leftover exactly like the references.
  - *Keypad grids fill the viewport:* `hexpand` + row/column-homogeneous, no `halign Center` (removed); CSS keeps the 336×236 block. Buttons measure 44 px tall as intended.
  - *Converter panel:* DropDowns get `halign Start` (chevron sits text-adjacent as in the reference; `hexpand` kept so the category row still spans), the second value gains `margin-top: 36` (upstream `textview:not(:first-child)`), the fields box is `vexpand` + `valign Center` (pair centered in the leftover), root padding `12px 12px 0 12px`.
  - *Caret visibility:* the entry TextView grabs focus at startup and after every solve, so the caret shows as in the reference screenshots.
  - *Window minimum 360×616* (was 300 wide): upstream's 336 px keypad grid + 24 px margins floor the width at 360; a 300 px window squeezed columns below the spec cell size.
- **D25 Header/menus + programming keypad parity (the prompt owner's "make the mode switching menu the same, make the hamburger buttons work, make the header one color" round, with a programming-wide parity pair).** Four workstreams, each screenshot-verified against GNOME 51 references with the Xvfb harness (`/tmp/ai-agent/vis25b.sh`).
  - *Menus are real `gio::Menu` models on actions (upstream `math-window.blp` parity), not decorative widgets.* The mode MenuButton opens a single radio section on the stateful `win.mode` action; the hamburger opens the primary menu — New Window | Clear History (`hidden-when: action-disabled`, so it vanishes in conversion mode) | a "Result Format" section (Automatic/Fixed/Scientific/Engineering on `win.number-format`) | Preferences / Keyboard Shortcuts / Help / About Calculator. Accelerators registered with `app.set_accels_for_action` (Ctrl+N, Ctrl+Q, F1, Ctrl+?, Ctrl+comma, Ctrl+Escape, the Ctrl+Alt+*mode letters*) are rendered by the popovers' keycap column automatically — no per-item accel attributes needed; the mode menu shows radio dots for the active mode.
  - *Flat header.* `@define-color headerbar_bg_color @window_bg_color` at the top of `load_css`: libadwaita's default headerbar shade made the header a visibly lighter band than the content; the GNOME 51 reference header is the window color.
  - *Programming keypad upstream parity.* The base (Binary/Octal/Decimal/Hexadecimal) and word-size (8/16/32/64-bit) selectors are labelled up-opening MenuButtons ("Decimal", "64-bit") in the keypad grid's bottom row (each spanning 2 columns, `function-button`, `can-shrink`, non-focusable), like upstream; the bit panel keeps its wide two-row 64-toggle form inside the display card ≥ 700 px and re-parents onto a third carousel page below 700 px (four 16-bit rows, `.bit-panel.in-carousel` drops the card chrome) — `ProgrammingPads::set_collapsed(c, card)` moves it back and forth under a `Cell<bool>` guard (a widget with a parent silently fails the second `append`).
  - *Keypad cell size comes from the grid floor, not per-button minimums.* `.math-buttons` keeps the 336×236 CSS floor (5×64/44 cells); the per-button `min-width/min-height` were dropped. Load-bearing for programming: its hex columns place 5 narrow digit columns inside 3 main columns, and per-button minimums forced those cells to full button width — overflowing the 700 px window. Homogeneous grids distribute whatever the floor gives.
  - *Breakpoint focus steal (the D25 blocker: pressing Return on startup opened the hamburger menu).* Root cause, end to end: adw::BreakpointBin's transition saves `last_focus`, hides the child for a frame (`gtk_widget_set_child_visible(FALSE)` — focus cleared to `<none>`), and schedules `breakpoint_changed_tick_cb` to restore it — but a `::focus` vfunc query during that window *cancels the restore* (`g_clear_weak_pointer(&priv->last_focus)`) and queues a full focus walk instead, which lands on the first focusable widgets: the header MenuButtons' internal GtkToggleButtons (GTK 4.24's MenuButton wraps an internal toggle). The next Return then activated hamburger/mode/base → popover opened → keyboard grabbed. At startup this always fired because `tv.grab_focus()` ran before `window.present()` (silently dropped on an unmapped window). Fixes, all in `win.rs`: grab focus only *after* `present()`; keep the `adw::Breakpoint` (a width-notify cannot replace it — GTK clamps programmatic resizes to the *current* content minimum, so the wide layout's ~700 px minimum blocked shrinking to 360 px; the bin evaluates conditions pre-allocation, which is exactly why the breakpoint can) and re-grab the entry 50 ms after every apply/unapply (`refocus_after_breakpoint`). 50 ms because the bin's tick always runs within one frame; an `idle_add` raced it and lost non-deterministically. The re-grab skips when a menu is active (don't fight an open popover's keyboard grab).
  - *Typing race + radix-point routing (found by the harness).* The 50 ms solve poll let `show_result`'s `buffer.set_text` wipe characters typed within the window after Return ("5/6" → "6"); the poll is 10 ms. The plain `.` key had no `handle_key` mapping (only KP_Decimal did), so the TextView inserted it natively — bypassing `insert()`'s undo snapshot and fresh-start-after-answer rule; `'.' => Some((".".into(), false))` now routes it like the keypad dot.
- **D26 License = MIT (superseded by D34: Radix is GPL-3.0-or-later).** The scaffold was set to GPL-3.0-or-later; the owner corrected it to MIT. Applied everywhere: workspace `Cargo.toml` (`license = "GPL-3.0-or-later"`), a root `LICENSE` file (MIT text, "The Radix Authors" — swap in the owner's legal name if preferred), README, and the About dialog (`dialogs.rs` `License::Gpl30` — a deliberate deviation from doc 06 §3, which mirrors upstream's GPL-3.0 About display; the dialog states Radix's own license). The LGPL dependencies (`rug`/GMP/MPFR/MPC, gtk4/libadwaita is MIT) remain fine under MIT: LGPL obligations attach to the library, not the application using it, so D1's dependency choice stands — only the licensing clause was superseded. Superseded by D34 — its premise was disproved: Radix is a derivative work of GNOME Calculator (the derivation reaches into the git history) and carries upstream's license.
